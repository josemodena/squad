# Squad 0.7.0

The review cycle becomes the rule, every piece is planned under Why, What and
How, and the delivery mechanics move into scripts. This release also carries
the 0.6.1 and 0.6.2 builds, which were not published on their own.

## Changes

**The review cycle is the rule.** A new shared document,
[the review cycle](https://github.com/josemodena/squad/blob/v0.7.0/docs/roles/review-cycle.md),
sets it out, and the engineer, engineering-reviewer, project-manager, plan and
retro skills follow it: machine gates before any Reviewer, pull requests of
about 400 non-test lines, one review scoped to the diff and the acceptance
criteria with each finding blocking or note, notes that do not block, a named
fix checked by the merger with no second review unless behaviour changes,
fixtures never written by the Engineer, two full test suites at once at most,
and one cold run mid-sprint.

**Why, What, How.** The piece template has three headings. The Why says in
plain words the reason, the consequence of not doing it and the goal it serves;
the acceptance test sits under How. `squad.sh issue` writes this body when none
is given, and every follow-up issue carries all three headings.

**Verdicts and merging.** `review-record` now writes the verdict line that
`squad.sh merge` reads: `Verdict: merge`, `merge after named fixes` or
`do not merge`, then the reviewed head, with the
`<!-- squad-review-passed:<sha> -->` marker on a pass. `squad.sh merge PR ISSUE`
checks the verdict, accepts a named fix once a later comment names the new head,
runs `gitw.sh finish`, moves every closed issue to Done and posts the close-out.
When a step fails after GitHub has merged, it finishes the rest and lists the
failures. `launch`, `at-pr` and `verdict` cover the other board upkeep.

**Rate limits.** Board writes take one full backup per session instead of one
per write and pause between writes (`SQUAD_WRITE_PAUSE`, default 3 seconds).
`squad.sh issue` checks the GitHub rate budget before it creates anything.
`squad.sh place` sets status, sprint, iteration and estimate in one call.

**Capacity.** `claude-quota` reads every weekly meter in the usage file, not
only the all-models one, and takes its verdict from the meter with less headroom.

**Claude Code.** The job runtime is off by default (`job_runtime: off`): Status
on the board is the state, and claims, checkpoints, Stage and Responsible role
are retired. `gitw.sh start` creates each piece's worktree under the scratch
root. Housekeeping prunes the Docker build cache and read-only scratch trees.
Hooks read their input before any early exit, and the PreCompact hand-over
blocks compaction when it cannot run, as Claude Code 2.1.299 expects.

## Upgrade

Update the marketplace and the plugin at every scope you installed it:

```bash
claude plugin marketplace update squad
claude plugin update squad@squad
claude plugin update squad@squad --scope project   # from each project using it
```

Start a new harness session afterwards. A project that relies on the job runtime
sets `job_runtime: on` in its settings file; Codex keeps it on by default. No board
migration is needed. Existing issue templates are not overwritten: copy the new
piece template from the plugin's `templates/piece.md` into
`.github/ISSUE_TEMPLATE/` to adopt Why, What, How.

## Validation and limits

`bash tools/test.sh` passes: the repository checks, the Python runtime and
board-backup suites, both plugins' shell self-tests, finish guards and
housekeeping fixtures, and the Go App Server tests with the race detector. The
fixtures do not call GitHub or a model. `selftest.sh` also runs clean inside
the plugin-only archive and a marketplace install, where it skips the manifest
check that needs a checkout. The Codex plugin shares the runtime, the
role documents and the piece template, but its skills were not rewritten for the
review cycle and it was not exercised live in this release.
