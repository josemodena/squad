# Squad 0.5.1 — Lower GitHub API usage

Squad now shares routine board reads and checks the selected task again before
claiming it. These changes work with free GitHub accounts and apply to both plugins.

- `board`, `ready` and `next` share a 60-second cache with visible age; `--fresh`
  forces a complete refresh. Claims always make a targeted live readiness read.
- Readiness queries request fewer nested fields and still finish pagination.
- `fields ISSUE --file FILE` applies a complete field handoff using one fresh
  backup, validates all requested values first, skips no-ops and verifies the item.
- Issue-only blocker edits retain versioned issue backups and journals without
  exporting the whole Project. Project mutations keep full fresh backups.
- A shared local transport coordinates typed API requests across projects, records
  usage and persists rate-limit cooldowns. The conductor can wake after reset.
- Typed issue/PR reads use REST. Single-page reply polls support conditional reads
  and keep a stable cursor when nothing changes.

## Updating

Update both your plugin and the CLI checkout. Use a fresh agent session after
checkpointing active work so the Administrator receives the grouped-handoff
instructions. No board migration, new token, paid plan or webhook receiver is needed.
Defaults apply to existing configurations. Do not restart active delivery jobs.

See [GitHub API usage](https://github.com/josemodena/squad/blob/v0.5.1/docs/guides/github-api.md)
for commands, configuration, storage isolation and recovery.

## Validation and limits

Fixtures cover cache isolation, fresh claims, nested dependency pagination,
shared cooldowns, reset wake-up, user pauses, conditional replies, incomplete PR
reads, partial mutation handling, and a grouped handoff preserving Status and
option identities. Existing backup, migration, runtime and conductor checks remain.

A live read-only comparison on a 117-item board reduced a full readiness read
from 157 GraphQL points to seven (about 95.5%), with identical populated planning
data and readiness results. Each version made four requests. A repeated cached
read made no request; fetching one selected issue used one request and one point.
This is a measured example, not a guarantee for every board. Production
board mutations were not used for release testing; write safety uses fixtures.

Some legacy shell and direct GitHub CLI operations remain outside the coordinated
transport; `api-status` does not represent all account traffic. Coordination is
local to one machine. Project REST replacement and a hosted webhook receiver are
not enabled in this release. Grouped writes are journalled, not remotely atomic;
reconcile partial results before retrying.
